# Bounded module and profile discovery

`AndUEProber::Probe` exposes ELF64 little-endian AArch64 module discovery through `Discovery.hpp`. `readModuleImage` reads and rechecks the ELF and program headers, accepts at most 64 program headers, validates load-range overlap, alignment, file and address overflow, and requires the headers inside readable load ranges. The caller supplies the normal-linker relocation base, module identity and live generation; the image does not own its memory.

`findAdrpReference`, `findObjectArrayCandidate` and `findNameToStringCandidate` receive the same `MemoryReader`, `ModuleImage` and `ReadBudget`. Every scan, instruction and pointer read consumes that budget, including cancellation, deadline and generation checks before and after the provider returns. Permission, short-read, unmapped, overflow and capacity errors propagate as `Status`. No helper caches addresses.

String scans examine readable `PT_LOAD` ranges in 4096-byte portions with bounded overlap. Instruction scans examine readable executable ranges and require adjacent AArch64 ADRP/ADD or ADRP/LDR pairs with matching registers. ADRP's architectural 4096-byte page is independent of the Android mapping page size. The helpers do not mask pointer tags, infer instruction sequences across register-clobbering instructions, or establish generic ABI support.

Object-array discovery requires a unique UTF-16 shutdown string, a unique adjacent ADRP/ADD reference, a bounded frame prologue, a bounded return, an in-module call target and a unique readable global pointer candidate. The pointer slot is reread before publication. Name-to-string discovery observes a unique call target near its declared string and prologue. Unconditional branches, ambiguous matches and unsupported sequences fail visibly. These heuristics can reject valid compiler output; they do not prove function identity or callable signatures.

`DiscoveryValue` records a candidate address and evidence containing module identity, lease generation and relative observation addresses. A candidate remains `Validation::Candidate` when captured in a session. The frozen result records what was observed; the module lease does not make mutable engine memory a coherent snapshot. A discovered call address never enables an engine call. No discovered address is registered with the compiled text-shim executor; raw UE text invocation remains `Unsupported`.

## Android integration

`ProcessMemory::openByName` accepts one to sixteen exact module basenames. Selection uses the normal loader's `dl_iterate_phdr` records, bounded to 4096 modules and 64 program headers per module. Ambiguous names fail. `open` acquires an existing module reference with `RTLD_NOLOAD`, validates the selected path and rejects multiple loader instances with the same path or device/inode identity, reads bounded GNU build-ID notes and assigns a non-reused lease generation. When supplied, the operation budget also covers identity-note reads. Manually mapped, headerless or concealed modules have no supported provider.

`DetectAndPrepareGame` selects only a profile declared for the current explicitly initialized process. Seven first-party profile descriptors use bounded discovery in exact `libUE4.so` or `libUnreal.so` linker modules. The 26 pinned upstream profile descriptors are inventoried but rejected before their unbounded discovery functions run. First-party parameterless upstream discovery and name-resolution methods are disabled because those interfaces cannot receive a reader, budget, module lease or executor contract.

The profile adapter reads object-array metadata through Core and stores the discovery provenance in the immutable observation. Custom/encrypted names have no configured bounded name provider. Profile names and package IDs are source inventory, not target authorization or demonstrated compatibility. No profile or game package is exercised by the discovery runtime fixtures.

The standard agent does not call upstream `GetUnrealELF`, `findIdaPattern`, `InitUEVars`, `findProcessEvent`, `UEDumper::Init` or live `UEDumper::Dump`. ProcessEvent discovery and full SDK generation return `Unsupported`. Full SDK support requires a bounded reflection-to-dumper snapshot adapter; this is an implementation gate. The independently tested frozen observation exporter and pinned SDKCoreGen array subset remain available.

## Fixtures and traceability

`tests/discovery.cpp` uses an independently encoded synthetic ELF and AArch64 instruction image. It calls the production helpers for cross-portion literals, negative displacements, changed pointer slots, duplicate candidates, malformed headers, overflow, permissions, short reads, cancellation, deadlines and lease generations. A real `Session` freezes candidate evidence and export validation rejects unvalidated discovery candidates.

`tests/profile_discovery.cpp` calls the actual first-party helper and `GameProfileEx` adapter against that owned image. The upstream-profile rejection case verifies that it performs no reads. `tests/process_memory.cpp` uses a separately compiled owned DSO for exact linker selection, bounded ELF/header reads, initialization failures, eight normal unload/reload lease cycles and Android FORCE_LOAD duplication of the same owned DSO. Both duplicate addresses must be rejected; removing the second instance permits a normal lease again. These tests do not execute decoded instructions or engine calls.

The slice addresses the discovery boundaries in R09, R13 and R18 with E05 fixtures. Configured Phase2–Phase4 use the Core structure, class and function probes with independent metadata. Configured FField base observations also use Core. Complete property probing returns Unsupported pending independent property/tail metadata and algorithms. The remaining Phase6 UEnum algorithm requires Core evidence migration and checked arithmetic at its call sites; its memory provider already shares the operation budget. Full reflected SDK generation, custom names and an owned UE application remain separate batch 08/09 gates.
