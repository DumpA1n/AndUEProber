# Bounded module and profile discovery

`AndUEProber::Probe` exposes ELF64 little-endian AArch64 module discovery through `Discovery.hpp`. `readModuleImage` accepts live or immutable file-backed ELF metadata, validates at most 64 program headers and produces bounded readable/executable `PT_LOAD` ranges relative to an explicit relocation base. File metadata supports admitted targets whose in-memory ELF header pages are absent; every candidate is still validated against current live mappings.

String scans process bounded chunks with overlap. Instruction scans decode adjacent AArch64 ADRP/ADD and ADRP/LDR pairs with matching registers and checked signed displacements. Object-array discovery follows the original FinishDestroy heuristic through a unique shutdown string, bounded function window and readable global relationship. Name-pool discovery scans the admitted profile patterns once across executable ranges. Every read consumes one operation budget and checks cancellation, deadline and generation before and after the provider call.

`ProcessMemory::openByName` supports exact normal-linker mappings in the current process. `openRemoteByName` supports an explicitly selected PID through an existing read-only `/proc/<pid>/mem` channel. Remote leases bind process start time, exact module path, load bias, inode and GNU Build ID and are revalidated between bounded operations. Neither path attaches, writes, changes protection or acquires privilege. Manually mapped, ambiguous, headerless-without-file-metadata and externally replaced mappings are rejected.

`DetectAndPrepareGame` admits only a profile whose package list matches the explicitly initialized package. All seven first-party and 26 pinned upstream profile classes receive the same bounded object/name discovery interface. Parameterless upstream scanners are not called. Profile-specific providers may override the common patterns; the Delta Force provider additionally implements its current encrypted narrow-name decoding contract. A decoded first live UObject and coherent object registry are required before a profile becomes active.

Discovery evidence records the module identity, generation, relative instruction/string locations and provider source. An address remains a candidate until the phase validates independent live relationships. ProcessEvent discovery similarly records an executable vtable candidate and index; it does not establish a callable signature and never authorizes invocation.

`tests/discovery.cpp` uses an independently encoded ELF/AArch64 image and covers cross-chunk literals, negative displacements, malformed headers, pointer changes, ambiguity, permissions, short reads, cancellation, deadlines and generations. `tests/profile_discovery.cpp` exercises the actual common and target-specific profile adapters. Android ProcessMemory fixtures cover exact PID/module selection and repeated loader generations. Target-runtime coverage is recorded separately in `docs/verification.json`.
